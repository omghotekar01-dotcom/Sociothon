# Private photograph upload recovery

Citizen report tracking provides English and Marathi photo recovery controls. Users may select a PNG or JPEG of up to 5 MB while the page is already loaded. Offline uploads are disabled. Reconnecting never uploads automatically, and the browser network indicator does not prove server reachability.

The selected file stays in memory only. The optional device-recovery checkbox permits storing a versioned upload identifier and SHA-256 fingerprint under the current account and case. Image bytes, filename, location and image metadata are not stored in browser storage. Switching reports, closing tracking or reloading discards the selected file. A consented reference restores the pending state when tracking is reopened; no reference is saved before an upload attempt. Preferences can clear this account's photo references together with other drafts.

An uncertain upload retains its identifier. Check photograph status calls `GET /api/v1/cases/{case_id}/evidence/submissions/{submission_key}`. The endpoint requires a current authenticated case participant or the report owner, and only returns photographs uploaded by that same account to that case. Knowing someone else's identifier does not reveal their photograph. A confirmed upload provides an authenticated link to the stored image, then clears the local reference when possible.

Retry first checks the server. If the photograph was committed, the interface recovers its confirmation without another POST or access to the original file. Otherwise the user selects the exact original file and explicitly retries. The browser compares its fingerprint; the server independently checks the submission identifier, bytes and notes. Changed files cannot reuse a pending identifier. Retrying a completed submission returns the original record and does not add another evidence or audit entry. Existing server image validation, metadata removal and download permissions still apply.

Malformed references remain on the device until explicitly cleared, with new selection blocked to avoid overwriting them. Storage failures are visible and do not claim successful persistence. Clearing a reference does not remove any server evidence; users are told to check its status before starting another upload. Rejected invalid images are not shown as synchronized. Switching reports creates a new upload component, preventing a selected file from carrying over to a different report.

Verification includes deliberate offline state, a response dropped after commit, a request aborted before commit, reload recovery without image storage, changed-file rejection, exact evidence/audit counts, report switching, invalid-image rejection, malformed references and simulated storage quota failure. API tests cover permissions, account/case isolation, logout, unchanged record identity and mismatched content. Browser checks use synthetic image fixtures and examine Marathi layouts at 390, 768 and 1440 pixels.

Limits: a selected image cannot survive a closed page; a retry before server commit requires the original file to be available again. The app shell and citizen draft entry are verified after online cache setup; the image itself still requires reopening tracking and selecting it again to retry a pre-commit failure. Without storage consent, pending information lasts only in the open tracking component. Browser storage is account-keyed application storage, not encryption. Cross-tab coordination, cross-device recovery and chunked/resumable large-file transfers are not implemented. There is no background synchronization or automatic retry.
